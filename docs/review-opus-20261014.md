# nai_ch_wiki の Opus レビュー（2026-10-14 JST）

**結論**
1. **wiki の写しは、遅くとも 7/26 から1ページも取れていない。** 毎朝「成功」と記録され、commit も push もされるが、中身はスレッドの写しだけ。wiki の中身の最後の更新は 4/7。
2. 原因は特定できた：7/26 の依存の更新で入った Scrapy 2.17 は、この spider が使う `start_requests()` をもう呼ばない。最初の1件の要求も出ず、0.002秒で「正常終了」している。直すのは数行（作業 R1014-RVh2）。
3. スレッドの写しは毎日きちんと動いている。repo の作りは小さく、過剰な作りは無い。直すのは「0件でも成功になる」所だけ。

## 指摘（重要な順）

1. **wiki の取得が0件のまま成功扱い（黙って止まる）** — 直す（手間：30〜60分、作業 R1014-RVh2）
   `seesawiki_back_up/spiders/backup.py` の `start_requests()` を `async def start(self)` に直す（Scrapy 2.13 からの新しい入口）。あわせて、取得したページが0件なら非ゼロで終わるようにする（今の試験9件はこの経路を通らない）。日次の記録の Scrapy の集計（`Crawled 0 pages`、`item_scraped_count` が無い）を見れば、毎日の失敗は確かめられる。

2. **一覧のページの取り方が壊れやすい** — 直す（上と同じ作業で）
   `parse()` は「次のページ」のリンクを `[0]` で取るので、最後のページで例外になる。またページの取得に失敗したときの再試行が `time.sleep(60)` で Scrapy 全体を止める。どちらも、直したあとに初めて表に出る。1回目の実行の記録を見て、最後のページで止まらないことを確かめる。

3. **`cron.log` が repo の中で伸び続ける** — 直す（手間：極小、急がない）
   Git の管理外だが、repo の中に日々の記録が溜まる。全体の規則では、生成されるものは repo の外。数 MB に育つまでは放置でよい。

4. **プロンプトのデータセットの取り込みとのつながり** — 残す（見落としの共有）
   別の repo（プロンプトのデータセット）にこの wiki からの取り込みの道具がある。wiki の写しが止まっていた間の新しいページは、そちらにも入っていない。直したあと最初の取得で追いつく。

## 残すべき良い所
- 日次の流れ：試験 → スレッド → wiki → 変わったときだけ commit。スレッドが失敗しても wiki は進め、終了コード2で知らせる、という区別。
- スレッドの「前スレ」をたどって抜けを埋める作り。毎日の変化を見る限り確実に動いている。
